## Topic 1: CPU调度算法

- cs102_k07: 短作业优先（SJF）调度算法选择估计运行时间最短的进程优先执行，其平均等待时间在所有非抢占式调度算法中最优...
- cs102_k08: 时间片轮转（Round Robin）调度算法将CPU处理时间划分为固定大小的时间片，就绪队列按FIFO排列...
- cs102_k09: 多级反馈队列（MLFQ）调度算法设置多个不同优先级的就绪队列，每个队列采用不同的时间片（高优先级队列时间片短）...
- cs102_k10: CPU调度算法的评价指标包括CPU利用率（CPU忙时间占比）、吞吐量（单位时间完成进程数）、周转时间（从提交到完成的总时间）...

### 现实案例
- **标题**：现实案例：医院急诊分诊台
- **正文**：医院急诊分诊台是CPU调度的真实写照。普通患者按挂号顺序就诊，像FCFS，但一位重症患者长时间占用医生会让后面小病患者苦等（护航效应）。如果优先处理预计诊疗时间短的患者，整体等待减少，类似SJF。若每位患者限看5分钟轮换，像时间片轮转（RR），保证公平响应。实际医院采用多级分诊：危急患者进最高优先级、快速处理；普通患者按顺序等待——这正是多级反馈队列（MLFQ）的思路，自适应不同类型患者并防止低优先级患者无限等待。

### 逐步示例
- **标题**：SRTF（抢占式短作业优先）调度过程与平均等待时间计算
- **进程信息**：P1(到达时间0, 运行时间7)、P2(到达时间2, 运行时间4)、P3(到达时间4, 运行时间1)、P4(到达时间5, 运行时间4)
- **步骤1**：t=0，仅 P1 到达 → P1 开始执行，剩余时间 7
- **步骤2**：t=2，P2 到达 → P1 剩余 5，P2 剩余 4。4 < 5，P2 抢占 P1，P2 开始执行
- **步骤3**：t=4，P3 到达 → P2 剩余 2，P3 剩余 1。1 < 2，P3 抢占 P2，P3 开始执行
- **步骤4**：t=5，P3 完成 → 就绪队列：P1(剩余5)、P2(剩余2)、P4(剩余4)。P2 剩余最短，P2 恢复执行
- **步骤5**：t=7，P2 完成 → 就绪队列：P1(剩余5)、P4(剩余4)。P4 剩余最短，P4 开始执行；t=11 P4 完成，P1 恢复执行至 t=16 完成
- **步骤6**：计算等待时间 → P1 等待 = 完成时间16 - 到达0 - 运行7 = 9；P2 = 7-2-4 = 1；P3 = 5-4-1 = 0；P4 = 11-5-4 = 2。平均等待时间 = (9+1+0+2)/4 = 3.0
- **执行甘特图**：P1(0-2) → P2(2-4) → P3(4-5) → P2(5-7) → P4(7-11) → P1(11-16)

### 主动练习 1（状态推演）
- **类型**：state_trace
- **题目**：三个进程 P1、P2、P3 同时到达（t=0），运行时间分别为 5、3、1。采用时间片轮转（RR）调度，时间片大小为 2。请推演完整的执行过程并给出最终完成顺序
- **初始状态**：就绪队列 [P1, P2, P3]，时间片 = 2
- **操作序列**：
  - 轮次1：P1 执行 2 个单位，P1 剩余 3 → 队列变为 [P2, P3, P1]
  - 轮次2：P2 执行 2 个单位，P2 剩余 1 → 队列变为 [P3, P1, P2]
  - 轮次3：P3 执行 1 个单位，P3 完成 → 队列变为 [P1, P2]
  - 轮次4：P1 执行 2 个单位，P1 剩余 1 → 队列变为 [P2, P1]
  - 轮次5：P2 执行 1 个单位，P2 完成 → 队列变为 [P1]
  - 轮次6：P1 执行 1 个单位，P1 完成 → 队列空
- **答案**：执行序列为 P1(0-2) → P2(2-4) → P3(4-5) → P1(5-7) → P2(7-8) → P1(8-9)。完成顺序为 P3 → P2 → P1。总完成时间为 9 个时间单位
- **反馈**：RR 调度按 FIFO 队列轮流执行，每个进程最多执行一个时间片后被抢占加入队尾。P3 运行时间仅 1，在第一轮中不足一个时间片即完成。注意 RR 中时间片大小的选择至关重要（知识切片 cs102_k08）：时间片过大退化为 FCFS，过小则上下文切换开销过大。此处时间片 2 使 P3 只执行 1 个单位就完成，不需额外等待第二轮
- **来源**：操作系统概念（Silberschatz）；知识切片 cs102_k08

### 主动练习 2（步骤排序）
- **类型**：step_order
- **题目**：在多级反馈队列（MLFQ）调度中，一个 CPU 密集型进程从进入系统到被定期提升优先级的完整流程。请将以下步骤排列为正确顺序
- **打乱步骤**：
  - A. 进程在 Q2（最低优先级队列，时间片最长）中执行
  - B. 新进程进入最高优先级队列 Q0（时间片最短）
  - C. Q0 时间片用完，进程未完成，被降级到 Q1（时间片更长）
  - D. 定期执行优先级提升（priority boost），将所有进程移回 Q0
  - E. Q1 时间片用完，进程仍未完成，被降级到 Q2
- **正确顺序**：B → C → E → A → D
- **反馈**：MLFQ 的核心机制是：新进程进入最高优先级队列 Q0（步骤 B），I/O 密集型进程通常在短时间片内完成或阻塞，留在高优先级队列获得快速响应；CPU 密集型进程在 Q0 时间片用完后降级到 Q1（步骤 C），再降级到 Q2（步骤 E），在 Q2 中以更长的时间片执行（步骤 A）。为防止低优先级进程饥饿，系统定期执行优先级提升（步骤 D），将所有进程移回 Q0。这与知识切片 cs102_k09 中"通过定期提升所有进程优先级可防止低优先级进程饥饿"的描述一致
- **来源**：操作系统概念（Silberschatz）；知识切片 cs102_k09

### 知识切片引用

- cs102_k13: 内存碎片分为内部碎片和外部碎片。内部碎片是已分配分区内部未被利用的空间，发生在固定分区或分页系统中...
- cs102_k14: 覆盖技术用于解决内存空间不足问题，将程序按调用关系分为多个覆盖段，不同段共享同一内存区域按需装入...

### 现实案例
- **标题**：现实案例：停车场车位分配策略
- **正文**：停车场管理是内存分配的直观类比。固定分区像划定的标准车位：一辆小车停进大车位，多出的空间浪费就是内部碎片。可变分区像灵活调整的车位隔板，按车辆大小动态划分，但反复进出后留下许多零散小空间无法停车，就是外部碎片。首次适应（FF）策略是从入口开始找第一个能停的车位，简单快速；最佳适应（BF）是找刚好能停的最小车位，省空间但留下大量太小碎片；最坏适应（WF）是找最大的车位停，减少小碎片但大车可能无处停。碎片太多时需要全部车辆挪动重新排列，对应紧凑技术。

### 逐步示例
- **标题**：首次适应（FF）与最佳适应（BF）在相同请求序列下的分配对比
- **初始空闲分区表**（按地址升序）：分区1=30K，分区2=20K，分区3=40K，分区4=10K
- **请求序列**：15K，10K
- **步骤1**：FF 分配 15K → 从表头查找，分区1(30K) >= 15K，分配。分区1 剩余 30-15=15K。空闲表：[15K, 20K, 40K, 10K]
- **步骤2**：FF 分配 10K → 从表头查找，分区1(15K) >= 10K，分配。分区1 剩余 15-10=5K。空闲表：[5K, 20K, 40K, 10K]
- **步骤3**：BF 分配 15K → 查找所有满足的分区：30K、20K、40K 均满足。选最小 20K，分配。分区2 剩余 20-15=5K。空闲表：[30K, 5K, 40K, 10K]
- **步骤4**：BF 分配 10K → 查找所有满足的分区：30K、40K、10K 均满足。选最小 10K（分区4），分配。分区4 剩余 0，移除。空闲表：[30K, 5K, 40K]
- **步骤5**：对比分析 → FF 后空闲表 [5K, 20K, 40K, 10K]，BF 后空闲表 [30K, 5K, 40K]。FF 在低址空间产生小碎片 5K；BF 保留了较大的 30K 分区但产生了无法利用的 5K 小碎片。知识切片 cs102_k12 指出 BF "产生大量小碎片"，FF "倾向于使用低址空间"

### 主动练习 1（状态推演）
- **类型**：state_trace
- **题目**：使用首次适应（FF）算法，给定初始空闲分区表和分配/释放请求序列，推演最终内存空闲状态
- **初始空闲表**（按地址升序）：[100K, 50K, 30K, 20K]
- **操作序列**：
  - 操作1：分配 60K
  - 操作2：分配 25K
  - 操作3：分配 15K
- **推演过程**：
  - 分配 60K：FF 从表头查找，100K >= 60K，分配。剩余 40K。空闲表：[40K, 50K, 30K, 20K]
  - 分配 25K：FF 从表头查找，40K >= 25K，分配。剩余 15K。空闲表：[15K, 50K, 30K, 20K]
  - 分配 15K：FF 从表头查找，15K >= 15K，正好分配。移除该分区。空闲表：[50K, 30K, 20K]
- **答案**：最终空闲分区表为 [50K, 30K, 20K]，总剩余空间 100K
- **反馈**：首次适应算法每次从链表头部开始顺序查找第一个满足大小的分区（知识切片 cs102_k12）。注意第三次分配 15K 时，第一个分区恰好等于请求大小，分配后剩余为 0，该分区从空闲链表中移除。如果使用最佳适应算法，第三次分配 15K 会选择 20K 分区而非 15K 分区，结果不同
- **来源**：操作系统概念（Silberschatz）；知识切片 cs102_k12

### 主动练习 2（代码填空）
- **类型**：code_fill
- **题目**：以下是用 C 语言实现的首次适应（First-Fit）内存分配算法，请填写空缺部分使分配逻辑正确
- **代码**：
```c
// 首次适应算法：从空闲分区数组头部查找第一个足够大的分区
// free_list: 空闲分区大小数组，n: 分区数量，request: 请求大小
// 返回分配的分区索引，-1 表示分配失败
int first_fit(int free_list[], int n, int request) {
    for (int i = 0; i < n; i++) {
        if (free_list[i] >= request) {
            int remaining = free_list[i] - request;
            free_list[i] = ________;  // 填空：更新分区剩余大小
            return i;
        }
    }
    return -1;
}
```
- **答案**：`remaining`
- **反馈**：首次适应算法找到第一个满足大小要求的分区后，将分区大小减去请求大小作为剩余空间。填入 `remaining`（即 `free_list[i] - request`）正确更新了分区剩余大小。若分区大小正好等于请求大小，remaining 为 0，表示该分区被完全占用。知识切片 cs102_k12 描述 FF "从链表头部开始查找第一个足够大的空闲分区"，代码中的 for 循环从头遍历体现了这一策略。注意最佳适应（BF）需要遍历所有分区选最小满足者，最坏适应（WF）选最大满足者
- **来源**：操作系统概念（Silberschatz）；知识切片 cs102_k12

### 知识切片引用
- cs102_k20: 分段管理将程序的逻辑地址空间按逻辑关系划分为多个段（如代码段、数据段、栈段），每个段有独立的段名和段长...
- cs102_k21: 段页式存储管理结合了分段和分页的优点，将用户程序按逻辑分段，每个段再划分为固定大小的页...
- cs102_k22: 虚拟地址到物理地址的转换是内存管理的核心机制。在分页系统中，MMU将虚拟地址分为页号和页内偏移...
- cs102_k23: 内存共享与保护是操作系统的重要功能。共享通过将不同进程的页表项映射到同一物理页框实现...

### 现实案例
- **标题**：现实案例：图书馆的两种书架管理方式
- **正文**：图书馆管理书籍有两种思路。分段管理像按学科分区：文学区、历史区、科技区各自独立，每个区有起始位置和大小，读者按"区名+区内位置"找书。好处是逻辑清晰、方便整区共享或限制权限，但各区大小不固定，反复增减后书架间出现无法利用的零散空隙（外部碎片）。段页式管理则是在每个学科区内再划分等高书架格（页）：先按学科找到区（段），再在区内按格号定位（页）。这样既保留学科分区的逻辑性和共享便利，又因格大小固定消除了区间的外部碎片，代价是找书需要查两次目录（段表+页表）。

### 逐步示例
- **标题**：段页式存储管理中的地址转换（三次访存）
- **系统参数**：页大小 = 4KB（4096 字节）
- **给定逻辑地址**：段号 S=1，段内页号 P=2，页内偏移 D=10（十进制）
- **步骤1**：第一次访存（查段表）→ 用段号 S=1 查段表，段表基址寄存器指向段表起始地址。段表[1] 记录该段的页表起始地址，假设为 0x5000
- **步骤2**：第二次访存（查页表）→ 用段内页号 P=2 查该段的页表。访问地址 = 页表起始地址 0x5000 + P × 页表项大小。页表[2] 记录物理页框号，假设为 15
- **步骤3**：计算物理地址 → 物理地址 = 物理页框号 × 页大小 + 页内偏移 = 15 × 4096 + 10 = 61440 + 10 = 61450
- **步骤4**：验证越界检查 → 段表项还包含段限长，需检查段内偏移（P × 页大小 + D = 2 × 4096 + 10 = 8202）是否超过段限长。若段限长 >= 8202 则地址合法
- **步骤5**：TLB 加速分析 → 知识切片 cs102_k21 指出段页式"地址转换开销较大，通常通过TLB加速"。若 TLB 缓存了段1页2的映射，则可直接得到页框号 15，省去两次访存，仅需一次访存获取数据

### 主动练习 1（输出预测）
- **类型**：output_predict
- **题目**：在纯分页系统中（非段页式），页大小为 4KB。给定虚拟地址 0x1005（十进制 4101），页表内容如下。请预测物理地址的十进制值
- **页表内容**：
  - 页号 0 → 物理页框号 3
  - 页号 1 → 物理页框号 7
  - 页号 2 → 物理页框号 5
- **代码/计算**：
```
页大小 = 4096 字节
虚拟地址 = 4101
页号 = 虚拟地址 / 页大小 = 4101 / 4096 = ?
页内偏移 = 虚拟地址 % 页大小 = 4101 % 4096 = ?
物理地址 = 物理页框号 × 页大小 + 页内偏移
```
- **答案**：页号 = 1，页内偏移 = 5，物理页框号 = 7，物理地址 = 7 × 4096 + 5 = 28677
- **反馈**：虚拟地址 4101 分解为页号 1（4101 / 4096 = 1 余 5），页内偏移 5。查页表得页号 1 对应物理页框号 7。物理地址 = 7 × 4096 + 5 = 28677。知识切片 cs102_k22 描述"MMU将虚拟地址分为页号和页内偏移，通过页号查页表得到物理页框号，与偏移拼接形成物理地址"。注意此题是纯分页（非段页式），地址转换仅需一次查页表，而段页式需要三次访存
- **来源**：操作系统概念（Silberschatz）；知识切片 cs102_k22

### 主动练习 2（状态推演）
- **类型**：state_trace
- **题目**：在纯分段存储管理中，给定段表和逻辑地址，推演地址转换过程并判断是否越界
- **段表内容**：
  - 段号 0：段基址 = 1000，段限长 = 400
  - 段号 1：段基址 = 3000，段限长 = 600
  - 段号 2：段基址 = 5000，段限长 = 500
- **逻辑地址**：段号 = 2，段内偏移 = 100
- **推演步骤**：
  - 步骤1：用段号 2 查段表 → 段表[2]: 段基址 = 5000，段限长 = 500
  - 步骤2：越界检查 → 段内偏移 100 < 段限长 500，未越界，地址合法
  - 步骤3：计算物理地址 → 物理地址 = 段基址 + 段内偏移 = 5000 + 100 = 5100
- **答案**：物理地址 = 5100，地址合法（未越界）
- **反馈**：分段管理中逻辑地址由段号和段内偏移组成（知识切片 cs102_k20）。地址转换时先用段号查段表得到段基址和段限长，再检查段内偏移是否越界，最后将段基址与段内偏移相加得到物理地址。若段内偏移超过段限长则触发越界异常（保护违例）。段表项中包含段基址和段限长是分段区别于分页的重要特征（知识切片 cs102_k22），分段便于实现段的共享和保护
- **来源**：操作系统概念（Silberschatz）；知识切片 cs102_k20、cs102_k23

- cs102_k25: 文件目录是文件控制块的有序集合，用于实现按名存取。目录结构包括单级目录（所有文件在一个目录中，命名冲突）...
- cs102_k26: inode（索引节点）是Unix/Linux文件系统的核心数据结构，存储文件的元数据（文件类型、权限、所有者、时间戳、文件大小）...
- cs102_k27: FAT（文件分配表）文件系统使用链式分配管理磁盘空间，FAT表记录每个簇的下一个簇号或结束标志...
- cs102_k28: 日志文件系统通过预写日志（WAL）保证文件系统一致性，将元数据修改先写入日志区域再应用到实际位置...

### 现实案例
- **标题**：现实案例：档案室的三种文件存放策略
- **正文**：档案室管理卷宗有三种方式，对应文件系统的三种磁盘块分配策略。连续分配像按编号将一卷档案存放在连续货架上，取档快、支持直接跳到中间页，但档案增长时无法扩展、撤档后留下不连续空架（外部碎片）。链接分配像每份档案标注下一份的位置，灵活扩展不需连续空间，但想跳到第50页必须从头逐份翻找，随机访问效率低。索引分配像每卷档案配一张目录卡，卡片上记录所有分册位置，支持随机访问且可动态增长，现代文件系统普遍采用此方案。inode 的多级索引则是索引分配的精妙升级：小文件直接用卡片上的指针定位，大文件用卡片指向二级目录册再查。

### 逐步示例
- **标题**：inode 多级索引结构计算文件最大容量
- **系统参数**：磁盘块大小 = 4KB（4096 字节），块指针大小 = 4 字节
- **inode 结构**：12 个直接块指针、1 个一级间接块指针、1 个二级间接块指针、1 个三级间接块指针
- **步骤1**：计算直接块容量 → 12 个直接块指针各指向一个数据块。直接块容量 = 12 × 4KB = 48KB
- **步骤2**：计算一级间接块容量 → 一级间接块是一个索引块，存储块指针。每个索引块可存 4096 / 4 = 1024 个指针。一级间接块容量 = 1024 × 4KB = 4MB
- **步骤3**：计算二级间接块容量 → 二级间接块指向 1024 个一级间接块，每个一级间接块再指向 1024 个数据块。二级间接块容量 = 1024 × 1024 × 4KB = 4GB
- **步骤4**：计算三级间接块容量 → 三级间接块指向 1024 个二级间接块。三级间接块容量 = 1024 × 1024 × 1024 × 4KB = 4TB
- **步骤5**：计算总容量 → 总最大文件大小 = 48KB + 4MB + 4GB + 4TB ≈ 4TB。知识切片 cs102_k26 指出 inode "使小文件直接索引快速访问，大文件通过间接索引支持大容量"
- **步骤6**：分析设计合理性 → 小文件（<= 48KB）仅需访问 inode 本身即可获取所有数据块地址，无需额外磁盘 I/O；大文件通过多级间接索引支持 TB 级存储，兼顾了访问效率和容量扩展

### 主动练习 2（步骤排序）
- **类型**：step_order
- **题目**：日志文件系统（如 ext3/ext4）在执行一次文件写操作时，为保证崩溃一致性，需按特定顺序执行步骤。请将以下步骤排列为正确顺序
- **打乱步骤**：
  - A. 文件系统将数据实际写入磁盘对应的数据块位置（checkpoint 阶段）
  - B. 应用程序发起文件写操作请求
  - C. 系统崩溃后重启，重放日志中已提交但未 checkpoint 的操作以恢复一致性
  - D. 文件系统将元数据修改记录写入磁盘日志区域（预写日志 WAL）
  - E. 日志记录写入完成并提交（journal commit）
  - F. 标记已 checkpoint 的日志记录为已完成，允许回收日志空间
- **正确顺序**：B → D → E → A → F → C（C 为崩溃恢复路径，正常运行时不含 C）
- **反馈**：日志文件系统的核心是预写日志（WAL）原则（知识切片 cs102_k28）：元数据修改必须先写入日志区域并提交（步骤 D → E），然后才能写入实际位置（步骤 A），最后标记日志记录可回收（步骤 F）。如果系统在步骤 A 之前崩溃，重启时重放已提交的日志（步骤 C）恢复到一致状态。这保证了"要么操作完全完成，要么完全未执行"的原子性。ext3/ext4 支持 journal、ordered、writeback 三种日志模式，权衡性能与可靠性
- **来源**：操作系统概念（Silberschatz）；知识切片 cs102_k28

## Topic 5: I/O系统与磁盘调度

### 知识切片引用
- cs102_k29: 设备驱动程序是操作系统内核中管理特定硬件设备的代码模块，为上层提供统一的设备无关接口...
- cs102_k30: 中断是设备通知CPU异步事件的机制，当设备完成I/O操作或发生错误时向CPU发送中断信号...
- cs102_k31: 直接存储器访问（DMA）允许外设与内存之间直接传输数据，无需CPU逐字节参与...
- cs102_k32: SCAN磁盘调度算法将磁头沿一个方向移动并服务沿途请求，到达磁盘边缘后反向继续服务，类似电梯运行模式...
- cs102_k33: C-SCAN（循环扫描）是SCAN的变体，磁头单向服务请求，到达边缘后快速返回到起始端不服务沿途请求...

### 现实案例
- **标题**：现实案例：电梯运行模式与磁盘调度
- **正文**：电梯运行方式完美对应磁盘调度算法。FCFS 像按呼叫顺序服务，谁先按谁先坐，但电梯频繁上下穿梭效率极低。SSTF（最短寻道时间优先）像总是去最近的楼层接人，效率高但远端的乘客可能永远等不到电梯（饥饿）。SCAN 像电梯单向运行到顶层再反向，沿途楼层顺路服务，类似真实电梯运行，各楼层等待时间较均衡。C-SCAN 像电梯只上行服务，到顶层后空降到一楼再开始上行，所有上行乘客等待时间更均匀。LOOK 是 SCAN 的改进：电梯不会傻傻跑到顶楼再折返，而是当前方向没有请求时立即反向。中断处理则像电梯到站铃响通知乘客，DMA 像快递员一次性搬完整个包裹无需收件人逐件确认。

### 逐步示例
- **标题**：SCAN 与 LOOK 磁盘调度算法的寻道序列与距离计算
- **初始条件**：磁头当前位置 = 53，移动方向 = 向磁道号增大方向，磁盘磁道范围 0-199
- **请求队列**：98, 183, 37, 122, 14, 124, 65, 67
- **步骤1**：SCAN 排序向高方向请求 → 当前方向（向高）的请求按磁道号升序：65, 67, 98, 122, 124, 183
- **步骤2**：SCAN 向高移动 → 53 → 65(寻道12) → 67(2) → 98(31) → 122(24) → 124(2) → 183(59) → 到达边缘 199(16)
- **步骤3**：SCAN 反向移动 → 199 → 37(寻道162) → 14(23)。向低方向请求按降序：37, 14
- **步骤4**：SCAN 总寻道距离 → 12+2+31+24+2+59+16+162+23 = 331
- **步骤5**：LOOK 变体计算 → LOOK 不走到边缘 199，183 后直接反向。序列：53→65→67→98→122→124→183→37→14。总寻道距离 = (183-53) + (183-14) = 130 + 169 = 299
- **步骤6**：对比分析 → LOOK 比 SCAN 少走 331-299=32 个磁道。知识切片 cs102_k32 指出 LOOK "在当前方向无请求时即反转，无需到达磁盘边缘"。SCAN 到达边缘 199 后才折返，多走了 199-183=16 个磁道的空行程

### 主动练习 1（状态推演）
- **类型**：state_trace
- **题目**：磁头当前位置 = 50，移动方向 = 向高磁道。请求队列：25, 80, 120, 10, 180。采用 C-SCAN（循环扫描）算法，磁道范围 0-199。请推演磁头移动序列并计算总寻道距离
- **推演过程**：
  - 向高方向服务（按升序）：50 → 80(30) → 120(40) → 180(60)
  - 到达最高请求 180 后，C-SCAN 继续到边缘 199(19)，然后快速返回到起始端 0(199)
  - 从 0 继续向高方向服务剩余请求（按升序）：0 → 10(10) → 25(15)
- **答案**：磁头移动序列 = 50 → 80 → 120 → 180 → 199 → 0 → 10 → 25。总寻道距离 = 30+40+60+19+199+10+15 = 373
- **反馈**：C-SCAN 只在向高方向服务请求，到达边缘后快速返回起始端不服务沿途请求（知识切片 cs102_k33）。注意 199→0 的折返距离 199 不服务任何请求。C-LOOK 变体则不走到边缘 199，到最高请求 180 后直接跳回最低请求 10，距离 = 30+40+60+(180-10)+15 = 315。C-SCAN 的优势是各请求等待时间更均匀，因为所有请求都在同一方向被服务
- **来源**：操作系统概念（Silberschatz）；知识切片 cs102_k33

### 主动练习 2（步骤排序）
- **类型**：step_order
- **题目**：DMA（直接存储器访问）方式完成一次磁盘数据传输的完整流程。请将以下步骤排列为正确顺序
- **打乱步骤**：
  - A. DMA 控制器在设备与内存之间直接传输数据块，CPU 同时执行其他任务
  - B. CPU 向 DMA 控制器初始化传输参数（源地址、目的地址、传输长度）
  - C. 数据块传输完成
  - D. CPU 响应中断，执行传输完成后的处理（如通知等待进程数据就绪）
  - E. CPU 向设备发出 I/O 命令，DMA 控制器接管总线控制权
  - F. DMA 控制器通过中断信号通知 CPU 传输结束
- **正确顺序**：B → E → A → C → F → D
- **反馈**：DMA 传输流程（知识切片 cs102_k31）：CPU 先初始化 DMA 参数（步骤 B），包括源地址、目的地址和传输长度，然后发出 I/O 命令让 DMA 控制器接管总线（步骤 E）。DMA 控制器在设备与内存间直接传输数据，CPU 无需逐字节参与可执行其他任务（步骤 A）。传输完成后（步骤 C），DMA 控制器通过中断通知 CPU（步骤 F），CPU 响应中断处理后续逻辑（步骤 D）。与中断驱动 I/O 每传输一个字节中断一次相比，DMA 以块为单位传输，大幅减少中断次数和 CPU 开销
- **来源**：操作系统概念（Silberschatz）；知识切片 cs102_k31

## Topic 6: 死锁

### 知识切片引用
- cs102_k34: 死锁产生的四个必要条件：互斥条件（资源同一时刻只能被一个进程使用）、占有并等待（进程保持已占资源并等待新资源）...
- cs102_k35: 银行家算法是经典的死锁避免算法，由Dijkstra提出。算法在每次资源分配前检查分配后系统是否处于安全状态...
- cs102_k36: 死锁预防通过破坏四个必要条件之一来防止死锁发生。破坏互斥条件：将资源改为可共享...
- cs102_k37: 死锁避免在资源分配过程中动态检查系统状态，确保不进入不安全状态，从而避免死锁...
- cs102_k38: 死锁检测允许系统进入死锁状态，通过算法周期性检测是否存在死锁并恢复...

### 现实案例
- **标题**：现实案例：十字路口的交通死锁
- **正文**：四辆车分别从东、南、西、北方向驶入一个没有红绿灯的十字路口，每辆车都占据了自己前方的车道（互斥条件），同时等待右前方那辆车让出车道（占有并等待），但没有车愿意倒车让路（不可抢占），四辆车形成"我等你、你等他、他等我"的循环等待链。四个必要条件同时成立，死锁发生，谁也动不了。解决办法有几种：安装红绿灯按序放行（破坏循环等待，对应资源有序分配）；要求车辆一次通过路口不许半途停留（破坏占有并等待）；设置交警强制指挥某车倒车（破坏不可抢占）。银行家算法则像银行贷款前审核：只有确认所有客户都能按序还清贷款才放贷，否则拒绝。

### 逐步示例
- **标题**：银行家算法安全性检查
- **系统资源**：两类资源 A 和 B，总量 A=6、B=4
- **进程状态**：
  | 进程 | Allocation(已分配) | Max(最大需求) | Need(仍需) |
  |------|---------------------|---------------|------------|
  | P0   | [3, 1]              | [5, 3]        | [2, 2]     |
  | P1   | [1, 1]              | [3, 2]        | [2, 1]     |
  | P2   | [1, 0]              | [2, 2]        | [1, 2]     |
- **Available（可用）** = 总量 - 已分配总和 = [6,4] - [5,2] = [1, 2]
- **步骤1**：检查 P0 → Need(P0)=[2,2]，Available=[1,2]。2 <= 1？否，P0 暂时无法完成，跳过
- **步骤2**：检查 P1 → Need(P1)=[2,1]，Available=[1,2]。2 <= 1？否，P1 暂时无法完成，跳过
- **步骤3**：检查 P2 → Need(P2)=[1,2]，Available=[1,2]。1<=1 且 2<=2？是！P2 可完成。P2 完成后释放已分配资源，Available = [1,2] + [1,0] = [2,2]。安全序列暂定 <P2>
- **步骤4**：回到 P0 → Need(P0)=[2,2]，Available=[2,2]。2<=2 且 2<=2？是！P0 可完成。Available = [2,2] + [3,1] = [5,3]。安全序列 <P2, P0>
- **步骤5**：检查 P1 → Need(P1)=[2,1]，Available=[5,3]。2<=5 且 1<=3？是！P1 可完成。Available = [5,3] + [1,1] = [6,4]。安全序列 <P2, P0, P1>
- **步骤6**：结论 → 存在安全序列 <P2, P0, P1>，系统当前处于安全状态，不会发生死锁。知识切片 cs102_k35 指出银行家算法"检查分配后系统是否处于安全状态：存在一个安全序列使所有进程能按某种顺序获得资源并完成执行"

### 主动练习 1（状态推演）
- **类型**：state_trace
- **题目**：基于上述银行家算法示例的初始状态，进程 P1 发起资源请求 Request(P1) = [1, 0]。请推演分配后的安全性检查结果，判断是否允许分配
- **初始状态**：Available = [1, 2]，Allocation(P1) = [1, 1]，Need(P1) = [2, 1]
- **推演步骤**：
  - 步骤1：检查 Request <= Need(P1) → [1,0] <= [2,1]？是，请求合法
  - 步骤2：检查 Request <= Available → [1,0] <= [1,2]？是，资源充足
  - 步骤3：试探性分配 → Available = [1,2]-[1,0] = [0,2]；Allocation(P1) = [1,1]+[1,0] = [2,1]；Need(P1) = [2,1]-[1,0] = [1,1]
  - 步骤4：安全性检查 → Available=[0,2]。P0 Need=[2,2]：2<=0？否。P1 Need=[1,1]：1<=0？否。P2 Need=[1,2]：1<=0？否。没有任何进程能完成！
- **答案**：不安全状态！试探分配后无法找到安全序列，系统拒绝分配，P1 必须等待
- **反馈**：银行家算法在每次分配前进行安全性检查（知识切片 cs102_k35、cs102_k37）。虽然 Request <= Need 且 Request <= Available，但试探分配后 Available 变为 [0,2]，没有任何进程的 Need 能被满足，进入不安全状态。因此系统回滚试探分配，让 P1 等待。死锁避免的核心是"确保不进入不安全状态"（知识切片 cs102_k37），而非直接检测死锁。注意不安全状态不等于死锁，但有可能导致死锁
- **来源**：操作系统概念（Silberschatz）；知识切片 cs102_k35、cs102_k37

- **答案**：填空1 为 `rec_stack`；填空2 为 `rec_stack[i]`
- **反馈**：检测环路是死锁检测的核心方法（知识切片 cs102_k38）。填空1 递归调用时传入 rec_stack 维护当前路径。填空2 检查邻接节点 i 是否已在当前递归路径上（rec_stack[i]==true），若是则存在从 i 到 v 再回 i 的环路，即循环等待条件成立。注意区分 visited（是否曾访问过）和 rec_stack（是否在当前路径上）：一个节点可能被访问过但不在当前路径中，此时不构成环。死锁四条件中循环等待是图论判定依据（知识切片 cs102_k34），资源分配图无环路则一定无死锁
- **来源**：操作系统概念（Silberschatz）；知识切片 cs102_k34、cs102_k38

## Topic 7: 同步与互斥

### 知识切片引用
- cs102_k39: 信号量是Dijkstra提出的同步工具，用整型变量和P/V（wait/signal）原子操作实现进程同步与互斥...
- cs102_k40: 互斥锁是实现临界区互斥访问的基本同步原语，提供加锁和解锁操作...
- cs102_k41: 条件变量用于线程间等待某个条件成立，通常与互斥锁配合使用...
- cs102_k42: 生产者消费者问题描述多个生产者向共享缓冲区写入数据、多个消费者从中读取数据的同步问题...
- cs102_k43: 读者写者问题描述多个读者和写者访问共享数据的同步问题，读者可并发读取但写者需独占访问...

### 现实案例
- **标题**：现实案例：停车场入口闸机与空位显示屏
- **正文**：停车场管理是同步与互斥的经典场景。入口闸机每次只允许一辆车通过，就像互斥锁保护临界区：车辆到达时若闸机空闲则进入（P操作/加锁），通过后闸机释放（V操作/解锁），同一时刻只有一辆车在闸机通道中。空位显示屏显示剩余车位数，就像计数信号量：每辆车进入时空位数减一（P操作），每辆车离开时空位数加一（V操作），空位为 0 时入口车辆阻塞等待。停车场还有入口和出口两个方向的显示屏需要同步更新，就像生产者消费者问题中的 empty 和 full 信号量：入口是"消费者"消耗空位，出口是"生产者"释放空位。如果显示屏数据被并发修改而不加保护，就会出现计数错误，这正是竞态条件。

### 逐步示例
- **标题**：生产者-消费者问题信号量执行过程推演
- **初始条件**：缓冲区大小 N=2，信号量初始值 mutex=1, empty=2, full=0
- **操作序列**：生产 → 生产 → 消费 → 生产 → 消费
- **步骤1**：生产者生产 → P(empty): empty=2-1=1 → P(mutex): mutex=1-1=0 → 写入数据 → V(mutex): mutex=0+1=1 → V(full): full=0+1=1。状态：{mutex:1, empty:1, full:1}
- **步骤2**：生产者生产 → P(empty): empty=1-1=0 → P(mutex): mutex=1-1=0 → 写入数据 → V(mutex): mutex=0+1=1 → V(full): full=1+1=2。状态：{mutex:1, empty:0, full:2}，缓冲区已满
- **步骤3**：消费者消费 → P(full): full=2-1=1 → P(mutex): mutex=1-1=0 → 读取数据 → V(mutex): mutex=0+1=1 → V(empty): empty=0+1=1。状态：{mutex:1, empty:1, full:1}
- **步骤4**：生产者生产 → P(empty): empty=1-1=0 → P(mutex): mutex=1-1=0 → 写入数据 → V(mutex): mutex=0+1=1 → V(full): full=1+1=2。状态：{mutex:1, empty:0, full:2}
- **步骤5**：消费者消费 → P(full): full=2-1=1 → P(mutex): mutex=1-1=0 → 读取数据 → V(mutex): mutex=0+1=1 → V(empty): empty=0+1=1。状态：{mutex:1, empty:1, full:1}
- **步骤6**：验证关键约束 → 知识切片 cs102_k42 指出 P 操作顺序"先获取资源信号量再获取互斥锁"。若生产者先 P(mutex) 再 P(empty)，当缓冲区满时（empty=0）生产者持有 mutex 后阻塞在 P(empty)，而消费者需要 P(mutex) 才能消费释放空位，导致死锁

### 主动练习 1（输出预测）
- **类型**：output_predict
- **题目**：以下生产者代码存在 P 操作顺序错误。当缓冲区已满（empty=0, full=N）时，预测程序运行结果
- **代码**：
```c
// 缓冲区大小 N=2，初始 mutex=1, empty=2, full=0
// 生产者代码（存在错误）
void producer() {
    while (true) {
        produce_item();
        P(mutex);    // 错误：先获取互斥锁
        P(empty);    // 再获取空位信号量
        put_item();
        V(mutex);
        V(full);
    }
}
```
- **答案**：程序将死锁。当缓冲区满时（empty=0），生产者先 P(mutex) 成功（mutex=0），然后 P(empty) 阻塞等待空位。但消费者需要先 P(mutex) 才能消费释放空位，而 mutex 已被生产者持有，消费者也阻塞。生产者和消费者互相等待，系统死锁
- **反馈**：正确的 P 操作顺序是先获取资源信号量（empty/full）再获取互斥锁（mutex）（知识切片 cs102_k42）。错误代码中生产者先 P(mutex) 再 P(empty)，当 empty=0 时生产者持有 mutex 却阻塞在 P(empty)，消费者无法获取 mutex 消费数据，形成死锁。这与死锁的"占有并等待"条件一致（知识切片 cs102_k34）：生产者占有 mutex 等待 empty，消费者等待 mutex。修复方法：交换 P(mutex) 和 P(empty) 的顺序，V 操作顺序不影响正确性
- **来源**：操作系统概念（Silberschatz）；知识切片 cs102_k42

### 主动练习 2（步骤排序）
- **类型**：step_order
- **题目**：条件变量配合互斥锁实现"等待条件成立"的正确流程。请将以下步骤排列为正确顺序
- **打乱步骤**：
  - A. 线程被唤醒后重新获取互斥锁
  - B. 线程获取互斥锁
  - C. 线程再次检查条件是否满足（防止虚假唤醒）
  - D. 条件不满足，线程调用 wait 操作（自动释放互斥锁并阻塞）
  - E. 另一线程修改共享状态后调用 signal/broadcast 唤醒等待线程
  - F. 线程在持有锁的状态下检查条件
  - G. 条件满足，线程执行后续逻辑并最终释放互斥锁
- **正确顺序**：B → F → D → E → A → C → G（其中 C 的循环路径为 C → 不满足则 D，满足则 G）
- **反馈**：条件变量的标准使用模式（知识切片 cs102_k41）：线程先获取互斥锁（步骤 B），在持有锁的状态下检查条件（步骤 F）。若条件不满足则调用 wait 操作释放锁并阻塞（步骤 D）。另一线程修改共享状态后调用 signal/broadcast 唤醒等待者（步骤 E）。被唤醒的线程重新获取互斥锁（步骤 A），再次检查条件防止虚假唤醒（步骤 C）。条件满足后执行后续逻辑并释放锁（步骤 G）。知识切片 cs102_k41 强调"wait操作通常放在while循环中"以处理虚假唤醒——即使被唤醒，条件也可能已被其他线程改变，必须重新检查
- **来源**：操作系统概念（Silberschatz）；知识切片 cs102_k41

## Topic 8: 进程间通信

### 知识切片引用
- cs102_k44: 管道是Unix系统最早的进程间通信机制，分为匿名管道和命名管道（FIFO）。匿名管道通过pipe系统调用创建...
- cs102_k45: 消息队列是内核维护的链表式消息容器，进程通过发送和接收消息进行通信...
- cs102_k46: 共享内存是进程间通信中效率最高的方式，多个进程将同一物理内存区域映射到各自虚拟地址空间...
- cs102_k47: 信号是一种异步通信机制，用于通知进程发生了某种事件。常见信号包括SIGINT（中断，Ctrl+C）...
- cs102_k48: Socket是支持网络通信的进程间通信机制，可用于同一主机或不同主机的进程间通信...

### 现实案例
- **标题**：现实案例：公司内部的五种沟通方式
- **正文**：公司不同部门间的沟通方式恰好对应五种进程间通信机制。管道像两人之间的传话筒：单向传递、缓冲区有限，只能用于关系密切的同事（父子进程）。消息队列像公司邮件系统：每封邮件有类型和正文，收件人可按类型筛选，发送者离开后邮件仍保存。共享内存像办公室的公共公告板：所有人直接看同一块板子，速度最快但需要排队规则（同步机制）防止同时涂改。信号像公司的警报铃：简单快速但信息量有限，只能通知"发生了什么事"（如火灾、下班），无法传递详细内容。Socket像跨地域的视频电话：既能用于同一楼层也能跨城市沟通，是分布式协作的基础，但需经过网络协议栈开销较大。

### 逐步示例
- **标题**：共享内存配合信号量实现进程间数据交换的完整流程
- **场景**：进程 A 写入数据，进程 B 读取数据，使用共享内存传输、信号量保证同步
- **步骤1**：创建共享内存 → 进程 A 调用 `shmget(IPC_KEY, 4096, IPC_CREAT|0666)` 创建 4KB 共享内存段，内核返回标识符 shmid
- **步骤2**：映射共享内存 → 进程 A 调用 `shmat(shmid, NULL, 0)` 将共享段映射到自己的虚拟地址空间，得到指针 `shm_addr_A`。进程 B 同样调用 `shmat` 映射同一共享段，得到指针 `shm_addr_B`。两指针指向同一物理内存
- **步骤3**：初始化同步信号量 → 创建互斥信号量 sem=1（初值1），用于保护共享内存的互斥访问
- **步骤4**：进程 A 写入数据 → A 执行 P(sem) 获取互斥（sem=0）→ 通过 `shm_addr_A` 写入数据 → V(sem) 释放互斥（sem=1）
- **步骤5**：进程 B 读取数据 → B 执行 P(sem) 获取互斥（sem=0）→ 通过 `shm_addr_B` 读取数据 → V(sem) 释放互斥（sem=1）
- **步骤6**：清理资源 → 通信完成后，两进程分别调用 `shmdt(shm_addr)` 解除映射。进程 A 调用 `shmctl(shmid, IPC_RMID, NULL)` 删除共享内存段。知识切片 cs102_k46 指出共享内存"多个进程将同一物理内存区域映射到各自虚拟地址空间，可直接读写共享数据无需内核拷贝"，但"需同步机制保证数据一致性"

### 主动练习 1（代码填空）
- **类型**：code_fill
- **题目**：以下代码实现父子进程通过匿名管道通信：子进程写入消息，父进程读取消息。请填写空缺部分
- **代码**：
```c
#include <unistd.h>
int fd[2];
pipe(fd);  // fd[0] = 读端, fd[1] = 写端

if (fork() == 0) {
    // 子进程：写入数据
    close(fd[0]);  // 关闭不使用的读端
    char msg[] = "hello parent";
    ________;  // 填空：通过管道写端写入消息
    close(fd[1]);
} else {
    // 父进程：读取数据
    close(fd[1]);  // 关闭不使用的写端
    char buf[64];
    read(fd[0], buf, sizeof(buf));
    printf("received: %s\n", buf);
    close(fd[0]);
}
```
- **答案**：`write(fd[1], msg, sizeof(msg))`
- **反馈**：管道是半双工通信机制（知识切片 cs102_k44），fd[0] 为读端、fd[1] 为写端。子进程写入数据使用 `write(fd[1], msg, sizeof(msg))` 通过写端发送。父进程通过 `read(fd[0], buf, sizeof(buf))` 从读端接收。注意每个进程应关闭不使用的端：子进程关闭读端 fd[0]，父进程关闭写端 fd[1]。如果父进程不关闭写端，当子进程写完关闭后，父进程的 read 会一直阻塞（因为写端未全部关闭，read 不会返回 EOF）。管道缓冲区有限（通常 64KB），写满时写入端阻塞，读空时读取端阻塞
- **来源**：操作系统概念（Silberschatz）；知识切片 cs102_k44

### 主动练习 2（步骤排序）
- **类型**：step_order
- **题目**：Socket 网络通信中服务器端从创建套接字到关闭连接的完整流程。请将以下步骤排列为正确顺序
- **打乱步骤**：
  - A. 服务器调用 accept() 等待并接受客户端连接（阻塞直到连接到达）
  - B. 服务器调用 socket() 创建套接字
  - C. 服务器调用 bind() 绑定 IP 地址和端口号
  - D. 通信结束，双方调用 close() 关闭套接字
  - E. 服务器调用 listen() 开始监听端口
  - F. 连接建立后，服务器通过新套接字与客户端进行 send/recv 数据通信
  - G. 客户端调用 connect() 向服务器发起连接请求
- **正确顺序**：B → C → E → A → G → F → D（其中 G 是客户端侧操作，与 A 同步进行）
- **反馈**：Socket 服务器端通信流程（知识切片 cs102_k48）：先创建套接字（步骤 B），再绑定地址和端口（步骤 C），然后开始监听（步骤 E），接着调用 accept 等待客户端连接（步骤 A）。客户端调用 connect 发起连接（步骤 G），accept 返回后连接建立。双方通过新套接字进行数据通信（步骤 F），通信结束后关闭套接字（步骤 D）。知识切片 cs102_k48 指出 Socket "通过IP地址和端口号标识通信端点，支持TCP（面向连接、可靠传输）和UDP（无连接、不可靠但高效）"。Socket 是唯一支持跨网络通信的 IPC 机制，而管道、消息队列、共享内存仅限同一主机
- **来源**：操作系统概念（Silberschatz）；知识切片 cs102_k48
