### 知识切片引用

- cs103_k02: TCP/IP模型是互联网实际使用的协议栈模型，将网络分为四层：网络接口层、网际层、传输层和应用层...
- cs103_k03: 数据在网络中传输时经历封装与解封装过程。发送端从应用层向下逐层添加协议首部...
- cs103_k04: OSI模型中层与层之间的交互通过服务访问点（SAP）实现。每一层通过SAP向其上层提供服务...

### 现实案例
- **标题**：现实案例：邮政系统分层投递
- **正文**：寄一封信时，你只需写好信纸装信封贴邮票投入邮箱，邮政内部按分拣、运输、投递等环节分层处理，每层只完成自己的职责。网络分层也是如此：应用层像写信人，传输层像装信封并标注收发人，网络层像分拣中心选择运输路线，数据链路层像运输车在相邻站点间搬运，物理层像公路本身。每层只与相邻层交互，互不干扰，只要接口不变就能独立演进——这正是分层架构模块化的优势。

### 逐步示例
- **标题**：HTTP GET请求从应用层到物理层的完整封装过程
- **步骤1**：应用层生成消息 → 浏览器构造"GET /index.html HTTP/1.1"请求行和首部字段，形成应用层消息（Message），PDU类型为Message
- **步骤2**：传输层添加TCP首部 → TCP在该消息前添加20字节首部（含源端口、目的端口80、序列号、确认号等），形成报文段（Segment），PDU变为Segment
- **步骤3**：网络层添加IP首部 → IP在报文段前添加20字节首部（含源IP、目的IP、TTL=64、协议号6等），形成数据报（Datagram），PDU变为Datagram
- **步骤4**：数据链路层添加帧首部和帧尾 → 以太网驱动添加14字节帧首部（含源MAC、目的MAC、类型0x0800）和4字节FCS校验尾，形成数据帧（Frame），PDU变为Frame
- **步骤5**：物理层转换为比特流 → 网卡将帧转换为电信号在线缆上传输，PDU变为比特流（Bit），接收端逐层向上解封装还原原始消息

### 主动练习 1（步骤排序）
- **类型**：step_order
- **题目**：以下是在TCP/IP模型中，发送端从应用层数据到物理层比特流的封装过程。请将打乱的步骤排列为正确的封装顺序
- **打乱步骤**：
  - A. 网络层添加IP首部（源IP、目的IP、TTL等）形成数据报
  - B. 物理层将帧转换为比特流在线路上传输
  - C. 应用层生成HTTP请求消息
  - D. 数据链路层添加帧首部（源MAC、目的MAC）和FCS帧尾形成数据帧
  - E. 传输层添加TCP首部（源端口、目的端口、序列号等）形成报文段
- **正确顺序**：C → E → A → D → B
- **反馈**：封装过程严格按从上到下的层次顺序进行：应用层先产生消息，传输层加TCP首部变报文段，网络层加IP首部变数据报，数据链路层加帧头帧尾变数据帧，最后物理层转为比特流。每一层的首部包含该层协议的控制信息（端口号、IP地址、MAC地址等），接收端逐层向上剥离首部完成解封装。这与知识切片 cs103_k03 所述"发送端从应用层向下逐层添加协议首部"一致
- **来源**：计算机网络：自顶向下方法（Kurose & Ross）；知识切片 cs103_k03

### 主动练习 2（状态推演）
- **类型**：state_trace
- **题目**：一个DNS查询消息从应用层发出，依次经过TCP/IP模型的各层。请推演该消息在每一层的协议数据单元（PDU）类型变化
- **初始状态**：应用层已生成DNS查询消息，PDU为Message
- **操作序列**：
  1. 传输层处理：添加UDP首部（8字节，含源端口、目的端口53）
  2. 网络层处理：添加IP首部（20字节，含源IP、目的IP）
  3. 数据链路层处理：添加以太网帧首部和FCS帧尾
  4. 物理层处理：转换为比特流在线路上传输
- **推演过程**：
  - 操作1后：PDU从 Message 变为 UDP Datagram（UDP用户数据报）
  - 操作2后：PDU从 UDP Datagram 变为 IP Datagram（IP数据报）
  - 操作3后：PDU从 IP Datagram 变为 Frame（数据帧）
  - 操作4后：PDU从 Frame 变为 Bits（比特流）
- **最终状态**：到达物理层时PDU为Bits（比特流），接收端将逆向从Bits逐层还原为Message
- **答案**：Message → UDP Datagram → IP Datagram → Frame → Bits；最终为 Bits（比特流）
- **反馈**：传输层PDU应按所用协议区分：TCP形成TCP Segment，UDP形成UDP Datagram；网络层再封装为IP Datagram。题面已明确本次查询添加UDP首部，因此本题选择UDP，但不能把DNS概括为“只使用UDP”：RFC 7766要求通用DNS实现同时支持UDP与TCP。知识切片 cs103_k03、cs103_k04提供了逐层封装和PDU独立性的基础
- **来源**：计算机网络：自顶向下方法（Kurose & Ross）；RFC 7766（DNS over TCP Requirements）；知识切片 cs103_k03、cs103_k04

### 现实案例
- **标题**：现实案例：办公楼门禁登记系统
- **正文**：办公楼的门禁卡上有唯一卡号（类比MAC地址48位唯一标识），前台登记卡号与办公室的对应关系（类比交换机MAC地址表）。访客刷卡时前台查表放行（类比交换机查表单播转发）；遇到未登记的卡号则广播通知所有楼层（类比泛洪）。不同部门可划分独立门禁区域互不干扰（类比VLAN隔离广播域），跨部门通行需经过前台转接（类比不同VLAN间需三层路由）。登记表有过期时间，长期未用的记录会自动删除（类比MAC地址老化机制）。

### 逐步示例
- **标题**：交换机MAC地址学习与帧转发过程
- **步骤1**：初始状态 → 交换机MAC地址表为空。端口1连接主机A（MAC=AA:AA），端口2连接主机B（MAC=BB:BB），端口3连接主机C（MAC=CC:CC）
- **步骤2**：主机A发送帧给主机C → 交换机从端口1收到帧，源MAC=AA:AA。将(AA:AA, 端口1)写入MAC地址表，完成地址学习
- **步骤3**：查找目的MAC=CC:CC → MAC地址表中无CC:CC的记录，交换机向除端口1外的所有端口（端口2、端口3）泛洪该帧
- **步骤4**：主机C收到帧并回复 → 主机C从端口3发送回复帧给主机A，源MAC=CC:CC。交换机将(CC:CC, 端口3)写入MAC地址表
- **步骤5**：查找目的MAC=AA:AA → 表中存在(AA:AA, 端口1)且不同于入端口3，交换机从端口1单播转发，不再泛洪。此后A与C之间的通信均通过查表精确转发

### 主动练习 1（状态推演）
- **类型**：state_trace
- **题目**：一台交换机有3个端口，初始MAC地址表为空。端口1连PC1(MAC=11)，端口2连PC2(MAC=22)，端口3连PC3(MAC=33)。请推演以下操作序列后交换机MAC地址表的内容
- **初始状态**：MAC地址表为空
- **操作序列**：
  1. PC1发送帧给PC3 → 交换机从端口1收帧，学习(11, 端口1)；表中无33，泛洪到端口2和端口3
  2. PC3回复帧给PC1 → 交换机从端口3收帧，学习(33, 端口3)；表中有11(端口1)，从端口1单播转发
  3. PC2发送帧给PC1 → 交换机从端口2收帧，学习(22, 端口2)；表中有11(端口1)，从端口1单播转发
- **最终状态**：MAC地址表包含3条记录：(11, 端口1)、(33, 端口3)、(22, 端口2)。此时三台主机互相通信均可查表单播转发，无需泛洪
- **答案**：(11, 端口1)、(33, 端口3)、(22, 端口2)
- **反馈**：交换机每次收到帧都执行两个动作：先学习源MAC与入端口的映射，再查表转发目的MAC。第一次通信时目的MAC不在表中，触发泛洪使帧到达所有端口；目标主机回复后其MAC也被学习，后续通信即可精确转发。交换机每个端口是独立冲突域，全双工模式下无冲突。这与知识切片 cs103_k07 所述"地址学习"和"查表转发"机制一致
- **来源**：计算机网络：自顶向下方法（Kurose & Ross）；知识切片 cs103_k07

### 主动练习 2（步骤排序）
- **类型**：step_order
- **题目**：以下是以太网CSMA/CD协议在节点发送数据时的工作流程。请将打乱的步骤排列为正确的执行顺序
- **打乱步骤**：
  - A. 边发边听——发送过程中持续检测信道上是否有冲突信号
  - B. 随机重发——采用二进制指数退避算法，等待随机时间槽后重新尝试发送
  - C. 先听后发——发送前先监听信道，信道空闲才开始发送
  - D. 冲突停发——检测到冲突立即停止发送，并发送Jam拥塞信号强化冲突
- **正确顺序**：C → A → D → B
- **反馈**：CSMA/CD的四个阶段按时间顺序为：先听后发（载波监听）→ 边发边听（冲突检测）→ 冲突停发（发送Jam信号）→ 随机重发（二进制指数退避）。第n次冲突后从0到2^k-1中随机选择等待时间（k=min(n,10)）。冲突检测要求帧发送时间大于信号往返传播时间，因此以太网规定最小帧长64字节。现代交换式以太网全双工模式下不存在冲突，CSMA/CD已不再需要。这与知识切片 cs103_k06 所述工作流程一致
- **来源**：计算机网络：自顶向下方法（Kurose & Ross）；IEEE 802.3标准；知识切片 cs103_k06

### 现实案例
- **标题**：现实案例：公司分机号系统
- **正文**：公司总机号码类比网络号，分机号类比主机号。行政部将8000-8099分给技术组、8100-8199分给市场组，相当于用子网掩码把一个大网分成多个子网。拨打分机时总机根据号段判断转接到哪个部门，就像路由器用子网掩码判断数据报属于哪个子网。若号码不够用还可以灵活调整号段边界，不再固守"技术组必须4位、市场组必须4位"的规则——这正是CIDR无类别划分的思路，打破了A/B/C类的固定边界。

### 逐步示例
- **标题**：将C类网络192.168.1.0/24划分为/26子网
- **步骤1**：确定原始网络 → C类网络192.168.1.0/24，子网掩码255.255.255.0，主机号8位，可容纳254台主机（主机号全0为网络地址、全1为广播地址不可分配）
- **步骤2**：选择子网掩码 → 使用/26即255.255.255.192，从主机号8位中借用2位作为子网号，剩余6位为主机号
- **步骤3**：计算子网数量 → 借用2位，可划分2^2=4个子网
- **步骤4**：计算每个子网的主机容量 → 剩余主机号6位，每个子网可分配2^6-2=62台主机（减去网络地址和广播地址）
- **步骤5**：确定各子网地址范围 → 子网0：192.168.1.0~63（网络地址.0，广播地址.63）；子网1：192.168.1.64~127（网络地址.64，广播地址.127）；子网2：192.168.1.128~191（网络地址.128，广播地址.191）；子网3：192.168.1.192~255（网络地址.192，广播地址.255）

### 主动练习 1（代码填空）
- **类型**：code_fill
- **题目**：以下Python代码通过IP地址和子网掩码计算网络地址。请填空使计算正确
- **代码**：
```python
ip = [192, 168, 1, 130]
mask = [255, 255, 255, 192]
network = []
for i in range(4):
    network.append(__________)  # 填入计算网络地址的表达式
print("网络地址:", ".".join(map(str, network)))
```
- **答案**：`ip[i] & mask[i]`
- **反馈**：网络地址通过IP地址与子网掩码按位与运算得到。Python中`&`是按位与运算符。逐字节计算：192&255=192, 168&255=168, 1&255=1, 130&192=128（130的二进制10000010与192的二进制11000000按位与得10000000即128）。因此网络地址为192.168.1.128，对应/26子网划分中的子网2。这与知识切片 cs103_k10 所述"子网掩码与IP地址按位与运算后得到网络地址"一致
- **来源**：计算机网络：自顶向下方法（Kurose & Ross）；知识切片 cs103_k10

### 主动练习 2（输出预测）
- **类型**：output_predict
- **题目**：路由器的路由表中有以下4条路由条目，目的地址为10.1.2.5的IP数据报到达后，路由器将选择哪个下一跳转发？请预测结果
- **路由表内容**：
```
目的网络          前缀长度  下一跳
10.0.0.0/8       /8       R1
10.1.0.0/16      /16      R2
10.1.2.0/24      /24      R3
0.0.0.0/0        /0       R4（默认路由）
```
- **预测内容**：目的地址10.1.2.5同时匹配4条路由（/8、/16、/24、/0），路由器按最长前缀匹配原则选择前缀最长的条目
- **答案**：选择R3（10.1.2.0/24），因为/24前缀长度最长（最具体），匹配最精确
- **反馈**：最长前缀匹配原则要求当多条路由都匹配目标地址时，选择前缀最长（最具体）的路由条目。10.1.2.5匹配/8（10.x.x.x）、/16（10.1.x.x）、/24（10.1.2.x）和/0（任意），其中/24前缀长度24最长，因此选R3。默认路由0.0.0.0/0前缀长度为0，是最后兜底选择。CIDR通过最长前缀匹配实现了路由聚合与精确路由的共存。这与知识切片 cs103_k11 所述"路由器选择前缀最长（最具体）的路由"一致
- **来源**：计算机网络：自顶向下方法（Kurose & Ross）；RFC 4632（CIDR）；知识切片 cs103_k11

## Topic 4: TCP流量控制与拥塞控制

### 知识切片引用
- cs103_k19: TCP滑动窗口是实现流量控制的核心机制。发送方维护发送窗口，窗口大小由接收方通过ACK报文段中的窗口字段（rwnd）通告...
- cs103_k20: 慢启动按确认新数据的ACK增加cwnd；持续发送且逐段确认时约呈指数增长，但延迟ACK会改变精确RTT序列...
- cs103_k21: 拥塞避免按确认新数据的ACK近似执行cwnd += SMSS*SMSS/cwnd，完整窗口持续发送时约每RTT增加1 SMSS，并非脱离ACK调度的固定时钟规则...
- cs103_k22: 第3个重复ACK到达时，按FlightSize计算ssthresh，立即重传丢失报文段，并把cwnd临时设为ssthresh+3 MSS进入快恢复...
- cs103_k23: 快恢复期间每个额外重复ACK可使cwnd增加1 MSS；确认重传数据的新ACK到达时，cwnd回落到ssthresh并进入拥塞避免...

### 现实案例
- **标题**：现实案例：水库调度系统
- **正文**：水库向下游供水时，闸门开度类比拥塞窗口（cwnd）。刚开始小开度试探（慢启动），确认河道能承受后逐步加大开度（指数增长）；到达警戒水位线（ssthresh）后改为缓慢增加（拥塞避免线性增长）。若发现下游严重溢洪（超时），立即关小闸门到最小重来；若只是局部波动（3个重复ACK），则只减半开度而非全关（快恢复）。下游水厂蓄水池容量类比接收窗口（rwnd），实际放水量取闸门开度和水厂容量的较小值——同时不淹没下游网络和不让水厂溢出。

### 逐步示例
- **标题**：TCP拥塞窗口从慢启动到快恢复的变化过程
- **步骤1**：慢启动阶段 → 本例固定每个满尺寸报文段由一个确认新数据的ACK单独确认且不使用延迟ACK。cwnd=1、ssthresh=16时，连续发送可按轮得到1→2→4→8→16
- **步骤2**：进入拥塞避免 → 本例把每轮完整窗口数据的ACK聚合为cwnd增加1 MSS的离散步骤：16→17→18→...→24；这是为状态推演固定的更新规则，不是脱离ACK调度的时钟保证
- **步骤3**：触发快重传 → 假设cwnd与FlightSize均为24 MSS时收到第3个重复ACK。按RFC 5681，ssthresh=max(FlightSize/2, 2 MSS)=12 MSS，立即重传丢失段，并把cwnd暂时膨胀为ssthresh+3 MSS=15 MSS
- **步骤4**：退出快恢复并继续拥塞避免 → 每多收到1个重复ACK，cwnd可再增加1 MSS；当确认重传段的新ACK到达时，将cwnd回落到ssthresh=12 MSS，再以线性方式增长：12→13→14→...
- **步骤5**：对比超时场景 → 若cwnd=24时不是收到3个重复ACK而是RTO超时，则ssthresh=24/2=12，cwnd重置为1，重新进入慢启动阶段（与快恢复的区别在于cwnd是否归1）

### 主动练习 1（状态推演）
- **类型**：state_trace
- **题目**：本题固定确认与离散更新规则：每个满尺寸报文段都由一个确认新数据的ACK单独确认，不使用延迟ACK；慢启动每轮按ACK增长，拥塞避免每完成一轮窗口数据后将cwnd增加1 MSS。一个TCP Reno连接初始cwnd=1、ssthresh=16（均以MSS为单位），请推演最终值

- **操作序列**：
  1. 按题设逐段确认规则完成4轮慢启动 → cwnd从1经2、4、8变为16，达到ssthresh
  2. 按题设离散更新规则完成2轮拥塞避免 → cwnd从16变为17，再变为18
  3. 此时FlightSize=18 MSS，收到第3个重复ACK → ssthresh=9 MSS，立即重传丢失段，cwnd=ssthresh+3 MSS=12 MSS

- **推演过程**：
  - 操作1后：cwnd=16, ssthresh=16（题设逐段确认，4轮为1→2→4→8→16）
  - 操作2后：cwnd=18, ssthresh=16（题设将每轮拥塞避免聚合为增加1 MSS）
  - 操作3后：cwnd=12 MSS, ssthresh=9 MSS（进入快恢复时用3个重复ACK暂时膨胀窗口）
  - 操作4收到新ACK后：cwnd=9 MSS, ssthresh=9 MSS（窗口回落）；再按题设完成1轮后cwnd=10 MSS
- **最终状态**：cwnd=10 MSS, ssthresh=9 MSS

### 主动练习 2（步骤排序）
- **类型**：step_order
- **题目**：本题固定确认与离散更新规则：每个满尺寸报文段都由一个确认新数据的ACK单独确认，不使用延迟ACK；慢启动每轮按ACK增长，拥塞避免每完成一轮窗口数据后将cwnd增加1 MSS。请排列该TCP Reno连接从慢启动到快恢复的题设事件

  - A. 收到第3个重复ACK，按FlightSize计算ssthresh，重传丢失段，并将cwnd设为ssthresh+3 MSS进入快恢复
  - B. 按题设逐段确认完成慢启动各轮，cwnd从1开始按1→2→4→8增长

- **来源**：计算机网络：自顶向下方法（Kurose & Ross）；RFC 5681第3.1节（Slow Start and Congestion Avoidance）、第3.2节（Fast Retransmit/Fast Recovery）、第4.2节（Generating Acknowledgments）；知识切片 cs103_k20、cs103_k21、cs103_k23

## Topic 5: UDP协议

### 知识切片引用
- cs103_k24: UDP是无连接的传输层协议，提供尽力而为的传输服务。首部仅8字节，包含源端口、目的端口、长度和校验和四个字段...
- cs103_k25: UDP校验和覆盖UDP首部和数据部分，还包含一个12字节的伪首部（含源IP、目的IP、协议号17和UDP长度）...
- cs103_k26（RFC 9000/9002 校正）：UDP适用于对实时性要求高、可容忍丢包的应用场景；标准QUIC在UDP之上提供多路复用、可靠交付与拥塞控制，丢失信息通过新帧重发，不把FEC作为标准核心恢复机制
- cs103_k27: TCP与UDP在设计目标上截然不同。TCP面向连接可靠有序，首部最小20字节；UDP无连接不可靠，首部仅8字节...

### 现实案例
- **标题**：现实案例：明信片投递
- **正文**：寄明信片不需要提前和邮局建立联系（无连接），写好地址直接投递，丢了邮局不负责你自己重寄（不可靠）。明信片轻便快捷（首部开销小仅8字节），适合寄简短通知如"图书馆几点开门"（DNS查询）。相比之下寄挂号信（TCP）要登记签收、保证送达，安全但繁琐耗时。如果只是问一句话，明信片足够了；但寄重要文件还得用挂号信。实时视频通话更像明信片——偶尔丢几帧无所谓，但延迟太大对方就听不清了，所以选UDP而非TCP。

### 逐步示例
- **标题**：UDP校验和伪首部的构造与计算过程
- **步骤1**：构造伪首部 → 伪首部共12字节，包含源IP地址（4字节）、目的IP地址（4字节）、协议号（1字节，值为17，补零到2字节）、UDP长度（2字节，含首部和数据）。伪首部不实际传输，仅用于校验和计算
- **步骤2**：组装待校验数据 → 将伪首部（12字节）+ UDP首部（8字节，校验和字段先置零）+ UDP数据按顺序拼接
- **步骤3**：按16位字分组 → 将拼接后的数据按每16位（2字节）为一组进行划分。若数据长度为奇数字节，末尾补零凑齐16位
- **步骤4**：反码求和 → 对所有16位字进行二进制反码求和。计算中将所有16位字相加，若有进位则回卷（将进位加回低位）
- **步骤5**：取反填入校验和字段 → 将求和结果取反码，填入UDP首部的校验和字段。接收方用相同方法计算后验证，若全1则正确，否则丢弃数据报

### 主动练习 2（状态推演）
- **类型**：state_trace
- **题目**：发送方依次通过UDP发送3个数据报D1、D2、D3，接收方无序号确认和重传机制。请推演以下网络传输操作后接收方的最终状态
- **初始状态**：发送方队列中有D1、D2、D3三个UDP数据报待发送，接收方缓存为空
- **操作序列**：
  1. D1进入网络后发生延迟 → D1尚未到达接收方，接收方缓存仍为空
  2. D2在网络中因拥塞被丢弃 → 接收方未收到D2，发送方不知道丢包（UDP无确认和重传机制）
  3. D3先于延迟的D1到达 → 接收方先收到D3，缓存中有[D3]
  4. 延迟的D1随后到达，D2始终未到达 → 接收方再收到D1，缓存变为[D3, D1]
- **推演过程**：
  - 操作1后：接收方缓存 = []（D1仍在网络中延迟）
  - 操作2后：接收方缓存 = []（D2丢失，UDP层没有确认或自动重传）
  - 操作3后：接收方缓存 = [D3]（后发送的D3先到达）
  - 操作4后：接收方缓存 = [D3, D1]（先发送的D1后到达，D2缺失）
- **最终状态**：接收方持有D3和D1，缺失D2，实际到达顺序为D3→D1，与发送顺序D1→D2→D3不同。UDP不保证可靠交付或顺序，也不会自动重传D2
- **答案**：接收方缓存为 [D3, D1]，D2 丢失且不会由 UDP 重传
- **反馈**：题面让后发送的D3先于延迟的D1到达，因此接收顺序确实为D3→D1；D2丢失后，UDP层不会收到确认或自动重传。需要可靠性时，应由UDP之上的协议实现。标准QUIC通过多路复用、确认与丢失检测、在新帧中重发信息以及拥塞控制提供可靠传输，不把FEC定义为核心恢复机制；对应RFC 9000第2节、第13.3节和RFC 9002第3节、第7节
- **来源**：计算机网络：自顶向下方法（Kurose & Ross）；RFC 768（UDP）；RFC 9000第2节、第13.3节；RFC 9002第3节、第7节；知识切片 cs103_k24、cs103_k27

## Topic 6: HTTP协议

### 知识切片引用
- cs103_k28: HTTP是请求-响应模型的应用层协议；HTTP/1.1和HTTP/2通常运行在TCP之上，HTTP/3运行在QUIC之上...
- cs103_k29: 安全方法只表示客户端没有请求目标资源状态改变，不排除日志或计费等附带副作用；幂等比较多个相同请求与单个请求的预期效果...
- cs103_k30: HTTP状态码按类别表达处理结果，常用状态包括200、201、301、304、400、401、403、404和500等...
- cs103_k31: HTTP/1.1默认使用持久连接；HTTP/2通过多路复用解决HTTP/1.1应用层队头阻塞，但不解决TCP队头阻塞...

### 现实案例
- **标题**：现实案例：餐厅同桌多份订单
- **正文**：HTTP/1.1管线化像服务员按顺序收下同桌多份订单，却必须按接单顺序逐份上菜；前一份耗时会挡住后面的成品，这是应用层队头阻塞。HTTP/2给每份订单编号并交错传递，某份订单的业务处理停顿时，其他流仍可继续。但所有订单仍装在同一辆TCP配送车里：若运输清单中间一页丢失，TCP必须先补齐缺口，后续页即使属于另一份订单也不能越序交给HTTP/2。多路复用解决的是HTTP/1.1的应用层顺序限制，不会消除底层TCP的按序交付约束。

### 逐步示例
- **标题**：两条HTTP/2流遇到TCP字节缺口时的交付过程
- **步骤1**：固定推演单位 → 为便于推演，把同一条TCP连接上的三个等长、连续字节范围简记为序号1、2、3；它们是TCP交付顺序，不是HTTP/2 stream ID
- **步骤2**：先交付序号1 → 序号1携带stream-1的数据并正常到达，TCP把它交给HTTP/2，下一段期望序号为2
- **步骤3**：形成缺口 → 序号2携带stream-1的数据但在网络中丢失；随后携带stream-3数据的序号3先到达，TCP缓存序号3，不能越过序号2的缺口交付
- **步骤4**：补齐并连续交付 → 序号2重传到达后，TCP先交付序号2，再立即交付已缓存的序号3，两条HTTP/2流才继续处理
- **步骤5**：区分两层队头阻塞 → HTTP/2流之间没有HTTP/1.1响应顺序约束，但同一TCP连接仍只有一条有序字节流；任一字节缺口都会暂时阻塞缺口之后的所有流数据

### 主动练习 2（状态推演）
- **类型**：state_trace
- **题目**：同一条TCP连接承载stream-1和stream-3两条HTTP/2流。把三个等长连续TCP字节范围简记为序号1、2、3；序号2丢失而序号3先到达。请推演TCP何时能把各字节范围交给HTTP/2
- **初始状态**：TCP下一段期望序号为1，接收缓存为空；序号1和2携带stream-1数据，序号3携带stream-3数据
- **操作序列**：
  1. 序号1到达 → 与期望序号一致，立即交给HTTP/2，下一段期望序号变为2
  2. 序号2丢失 → TCP仍等待序号2
  3. 序号3先到达 → TCP发现序号2形成字节缺口，只缓存序号3
  4. 序号2重传到达后 → 缺口补齐，TCP按序交付序号2和3
- **推演过程**：
  - 操作1后：HTTP/2收到序号1，TCP下一段期望序号为2
  - 操作3后：序号3不能越过缺口交给HTTP/2，即使它携带的是另一条stream-3的数据
  - 操作4后：TCP先交付序号2，再交付已缓存的序号3，stream-1和stream-3继续处理
- **最终状态**：HTTP/2按序收到序号1、2、3；序号3在序号2重传前一直留在TCP接收缓存
- **答案**：序号3不能越过缺口交给HTTP/2；序号2重传到达后，TCP才按序交付序号2和3
- **反馈**：HTTP/2多路复用解决HTTP/1.1的应用层队头阻塞，但RFC 9113明确指出它没有解决TCP队头阻塞。同一连接中位于缺口之后的其他HTTP/2流数据也会等待；不能把结论写成仅丢失数据所属的流受阻
- **来源**：RFC 9113第1节（HTTP/2的TCP队头阻塞边界）、第5节（Streams and Multiplexing）；知识切片 cs103_k31

### 现实案例
- **标题**：现实案例：城际公路导航
- **正文**：开车导航有两种思路。一种是只问路边当地人"下一个镇多远"（距离向量算法），每个路口的司机互相交换距离信息，逐渐拼出最短路线，但信息传播慢且可能以讹传讹（计数到无穷问题）。另一种是先获取全省完整公路地图（链路状态算法），自己用导航算法算出最短路径，准确快速但需要存储整张地图。城市间跨省行驶时，各省交通厅各自管理省内道路（OSPF内部网关协议），省际路口由国道编号指引（BGP外部网关协议），按行政策略而非纯距离选择跨省路径。

### 逐步示例
- **标题**：使用Dijkstra算法计算R1到R4的最短路径
- **步骤1**：初始化 → 源节点R1。已知直连链路距离：R1→R2=2，R1→R3=5。R4距离为无穷大。已确定集合S={R1}
- **步骤2**：选择最近节点 → R2距离最短（2），将R2加入S。S={R1,R2}。检查R2的邻居：R2→R3=1，因此R1→R2→R3=2+1=3 < 5，更新R3距离为3
- **步骤3**：选择下一个最近节点 → R3距离最短（3），将R3加入S。S={R1,R2,R3}。检查R3的邻居：R3→R4=4，因此R1→R2→R3→R4=3+4=7 < 无穷大，更新R4距离为7
- **步骤4**：选择下一个最近节点 → R4距离最短（7），将R4加入S。S={R1,R2,R3,R4}。所有节点已确定
- **步骤5**：确定最短路径 → R1到R4的最短路径为R1→R2→R3→R4，总距离=7。注意直连路径R1→R3=5虽短于R1→R2→R3=3的单独段，但经R2中转到R3（距离3）比直连（距离5）更优，链路状态算法通过全局拓扑发现了这一更优路径

### 主动练习 1（状态推演）
- **类型**：state_trace
- **题目**：路由器R1运行RIP协议（度量值为跳数），初始路由表如下。R2向R1发送了距离向量更新。请推演R1更新后的路由表
- **初始状态**：R1路由表：N1(距离0, 直连)、N2(距离2, 经R2)、N3(距离4, 经R3)。R2到各网段的距离：N1=1, N2=0, N3=1
- **操作序列**：
  1. R1收到R2的距离向量更新（R2到N1=1, N2=0, N3=1）
  2. 对N1：原距离0（直连）vs R2通告1+1=2，0 < 2，保持不变
  3. 对N2：原距离2（经R2）vs R2通告0+1=1，1 < 2，更新为距离1（经R2）
  4. 对N3：原距离4（经R3）vs R2通告1+1=2，2 < 4，更新为距离2（经R2）
- **推演过程**：
  - 操作2后：N1=0(直连)，保持不变（直连距离0最优）
  - 操作3后：N2=1(经R2)，从2更新为1（R2是N2的直连网段，经R2只需1跳）
  - 操作4后：N3=2(经R2)，从4更新为2（经R2到N3只需2跳，比经R3的4跳更短）
- **最终状态**：R1路由表为：N1=0(直连)、N2=1(经R2)、N3=2(经R2)。Bellman-Ford方程：新距离=min(原距离, 邻居到目标距离+到邻居距离)
- **答案**：N1=0（直连）、N2=1（经R2）、N3=2（经R2）
- **反馈**：距离向量算法使用Bellman-Ford方程更新路由：D(x,y)=min(D(x,y), D(x,v)+D(v,y))。R1收到R2的距离向量后，对每个目的网络比较原路径和新路径（经R2）的距离，取较小值。N1直连最优不更新，N2和N3经R2更短故更新。RIP每30秒交换距离向量，最大15跳限制防止计数到无穷。这与知识切片 cs103_k40、cs103_k41 所述Bellman-Ford方程和RIP机制一致
- **来源**：计算机网络：自顶向下方法（Kurose & Ross）；知识切片 cs103_k40、cs103_k41

- **反馈**：Hello协议先发现邻居并确认双向通信（B），随后进入ExStart协商主从关系和初始DD序列号（A）。进入Exchange后交换DBD摘要，同时邻接从Database Exchange开始即参与LSA泛洪（C）；Exchange中形成请求列表并可发送LSR，若列表未清空则进入Loading继续请求，接收LSU直至列表清空后到达Full（D）。RFC 2328第7.2节和第10.1节表明，泛洪不是“LSDB完整同步之后才开始”的独立后续阶段。只有因为题设固定拓扑并明确等待Full，最后才按当前区域LSDB运行Dijkstra生成路由表（E）
- **来源**：计算机网络：自顶向下方法（Kurose & Ross）；RFC 2328第7.2节（The Synchronization of Databases）、第10.1节（Neighbor states）、第16节（Calculation of the routing table）；知识切片 cs103_k42

### 现实案例
- **标题**：现实案例：密封信件与签章
- **正文**：对称加密像用同一把钥匙锁箱子和开箱子——快但钥匙怎么安全给对方是难题（密钥分发问题）。非对称加密像你有一把公开的锁（公钥），任何人都能锁上但只有你有钥匙（私钥）能打开。数字签名不是把开锁过程倒放：签名方按公开的签名方案让私钥参与生成签章，验证方把原文、签章、已可信绑定签名者身份的公钥和算法参数交给验证算法，得到有效或无效结果。实际通信中可用密钥交换或密钥封装建立对称密钥，再用对称算法保护大量数据；签名用于认证和完整性，不等同于加密内容。

### 逐步示例
- **标题**：混合加密通信的完整过程（RSA + AES）
- **步骤1**：生成对称密钥 → 发送方Alice生成一次性AES会话密钥K（如256位），用于加密大量数据，因AES加解密速度快适合大数据量
- **步骤2**：用公钥加密对称密钥 → Alice用接收方Bob的RSA公钥加密AES密钥K，得到密文C_key。RSA解决了对称密钥的安全分发问题
- **步骤3**：用对称密钥加密数据 → Alice用AES密钥K加密原始数据（如文件），得到密文C_data。AES加密速度远快于RSA，适合加密大量数据
- **步骤4**：发送密文 → Alice将C_key（加密的对称密钥）和C_data（加密的数据）一起发送给Bob
- **步骤5**：用私钥解密对称密钥 → Bob收到后，先用自己的RSA私钥解密C_key，恢复出AES密钥K。只有Bob的私钥能解密，保证了密钥分发的安全性
- **步骤6**：用对称密钥解密数据 → Bob用恢复的AES密钥K解密C_data，获得原始数据。整个过程中RSA仅用于加密少量数据（对称密钥），AES负责加密大量数据，兼顾了安全性和效率

### 主动练习 1（步骤排序）
- **类型**：step_order
- **题目**：接收方已通过有效证书路径或可信配置取得公钥，并确认该公钥与声称的签名者身份绑定。以下是数字签名的生成与验证过程，请将打乱的步骤排列为正确的执行顺序
- **打乱步骤**：
  - A. 接收方检查算法标识和参数符合本地策略，并选择对应验证算法
  - B. 发送方选择明确的签名方案（如RSA-PSS或ECDSA）及约定参数
  - C. 接收方以已可信绑定签名者身份的公钥、原消息、签名和约定参数调用验证算法，得到有效或无效结果
  - D. 发送方以私钥、原消息和约定参数调用签名算法；方案内部完成哈希与编码，输出数字签名
  - E. 接收方取得原消息和数字签名，并从协议上下文取得约定的算法标识和参数
- **正确顺序**：B → D → E → A → C
- **反馈**：发送方先选择明确的签名方案和约定参数（B），再以私钥、原消息和参数调用签名算法（D）；方案内部处理原消息并完成所需哈希与编码，这不是把摘要当普通密文加密后再由公钥解密。接收方取得原消息、签名及协议上下文中的算法信息（E），先检查算法与参数符合本地策略（A），再以已可信绑定签名者身份的公钥、原消息、签名和参数调用验证算法（C）。RFC 8017第8.1.1节把RSA-PSS签名接口定义为`RSASSA-PSS-SIGN(K, M)`，内部执行EMSA-PSS编码和RSA签名原语；第8.1.2节把验证接口定义为`RSASSA-PSS-VERIFY((n, e), M, S)`，内部执行RSA验证原语并检查EMSA-PSS一致性，最终返回有效或无效。数学验签有效只有结合可信公钥与身份绑定，才支持签名者认证；在私钥控制和审计等条件成立时，才可进一步作为不可否认性证据
- **来源**：NIST FIPS 186-5；RFC 8017第8.1.1节、第8.1.2节；知识切片 cs103_k46

### 主动练习 2（代码填空）
- **类型**：code_fill
- **题目**：以下Python代码使用AES-GCM模式进行认证加密。GCM模式同时提供机密性和完整性验证。请填入正确的模式构造方法
- **代码**：
```python
from cryptography.hazmat.primitives.ciphers import Cipher, algorithms, modes
from cryptography.hazmat.backends import default_backend
import os

key = os.urandom(32)    # AES-256 密钥（32字节）
nonce = os.urandom(12)  # GCM推荐12字节随机数

# 使用AES-GCM认证加密模式
cipher = Cipher(
    algorithms.AES(key),
    modes.____(nonce),   # 填入正确的GCM模式构造方法
    backend=default_backend()
)

encryptor = cipher.encryptor()
ciphertext = encryptor.update(plaintext) + encryptor.finalize()
tag = encryptor.tag      # GCM认证标签，用于完整性验证
```
- **答案**：`GCM`
- **反馈**：AES-GCM（Galois/Counter Mode）是认证加密模式，同时提供机密性（加密）和完整性（认证标签tag）。modes.GCM(nonce)创建GCM模式实例，加密后生成认证标签tag，解密时需验证tag。相比之下ECB模式不安全（相同明文产生相同密文），CBC模式需要额外的IV和MAC才能实现完整性验证，GCM将加密和认证合二为一。TLS 1.3仅支持AEAD模式（如GCM和ChaCha20-Poly1305），不再使用CBC等非认证加密模式。这与知识切片 cs103_k44 所述"GCM（认证加密，提供完整性验证）"一致
